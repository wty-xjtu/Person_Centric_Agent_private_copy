## 4.3 不完整需求的澄清与回应组织

本节按回应所依赖的信息来源比较两种处理方式：一是利用已有话语、用户条件与当前情境理解需求，组织可纠正的条件化回应；二是通过提问、候选方案和交互确认，以更低成本收集缺失信息并逐步逼近真实需求。

### 4.3.1 基于已有信息的需求理解与回应

本节讨论的核心问题是：在可用的用户信息与当前情境证据之上，系统如何组织本轮回应。传统任务型对话系统倾向于把回应生成视为“意图到动作”的映射；但 Personal Agent 的问题通常更复杂，往往需要把需求拆解为事实需求、行动需求、情绪需求和约束条件，并据此组织一轮回复。

基于已有信息的处理方式的第一类基础工作关注复杂话语的结构化整理。DialogUSR [R27] 针对用户在单一话语中表达多个意图的现象，提出先将其拆分为多个子需求，再分别解析；BlendX [R28] 进一步扩展到更复杂的混合意图检测场景，这类能力对 Personal Agent 的多目标支持很关键。

第二类工作强调回应必须嵌入情境才有意义。Dey [R32] 对情境建模的经典论述指出，时间、地点、活动和社会情境可以改变当前信息的意义；这一原则在 Personal Agent 中尤其重要，因为“我今天不想继续”同样的表述，可能在工作日、休息日、健康状态差或人际关系紧张时具有不同的实际意义。

情境解释还需要判断哪些个人信息与当前需求有关。RPEval 将偏好使用区分为 Ignore、Support 和 Dominate：有的偏好应被忽略，有的作为辅助条件，有的决定最终动作，这说明系统不能简单把用户画像全部嵌入回应，而要判断“这条偏好现在是否适用”。

第三类工作处理的是表面任务之外的支持需要。ESConv [R29] 定义了情绪支持对话任务，其框架建立在帮助技能理论之上，数据集中对支持策略（如安慰、共情、重构认知等）做了区分。这类需求不是单纯命令式提问，而是在用户情绪与状态不足时提供缓冲和方向。

多类需要并存时的组合问题由相邻工作揭示。Blended Skill Talk [R31] 指出，吸引人、有知识、有共情等品质此前多被孤立训练，而良好的开放域对话应当同时兼顾信息质量、关系维持和行动支持。对 Personal Agent，这意味着一轮回应往往需要同时处理事实、偏好与情绪，不能被简化为单一任务的生成。

适用条件方面，基于已有信息的处理方式要求已有话语与情境信息足以形成一个有依据的假设。当用户表达明确且情境充分时，系统可给出条件化的、可纠正的回应；但如果需求仍未稳定，系统就需要进一步澄清。对 Personal Agent 而言，现有工作的价值在于提供了明确“什么是已知条件、何时可以组织回应”的边界，并说明回应中应如何保留修正空间。

### 4.3.2 基于交互澄清的需求细化与回应

在进入具体方法之前，需要先界定本节要处理的问题：当用户的请求本身不足以支持唯一的回应时，系统应当如何组织这一轮的回应。与 4.3.1 讨论的“在已有信息下组织回答”不同，本节关注的是“需求尚未稳定，需要与用户互动才能确定”。

从问题界定转向机制比较，最早形成体系的一类工作来自开放域信息寻求对话领域。Aliannejadi 等人在 SIGIR 2019 的工作 [R21] 研究了信息需求不完整时如何生成澄清问题；其后由 MIMICS [R23] 与 MIMICS-Duo [R24] 等工作扩展到更大规模的搜索澄清设置，说明澄清并不是简单“追问”，而是为了确定用户真实意图和候选项差异。

第二类机制差异体现在澄清问题的生成与排序如何借助外部内容支撑。Mass 等人的混合主动会话搜索工作 [R25] 明确将任务设定为：在给定对话上下文的基础上，决定何时提问、提什么问题，并在候选检索结果中选择证据以支持澄清。此类工作强调澄清必须有“信息增益”，不是仅仅为了显得主动。

模型对歧义的处理还可以通过训练改变。APA 利用模型自身对歧义的感知进行对齐，使其显式检测和管理歧义查询，同时保留明确问题上的作答能力 [R26]。这说明澄清不是外部规则的简单插入，而可以成为模型行为策略的一部分。

第四类差异来自领域特化的澄清框架。ClarifyGPT [R34] 面向代码生成：它先通过代码一致性检查判断给定需求是否含歧义，若有歧义则提示大模型生成有针对性的澄清问题，以便收敛到可执行的任务定义。Ask-before-Plan [R37] 则把澄清扩展到真实世界规划：系统在做计划前检测是否需要先收集额外信息，再基于可用工具和环��状态推进行动。

澄清与下游协助的关系还可以在计划任务中检验。Ask-before-Plan 的指标对应三个子任务：Clarification Accuracy 检查澄清需要预测，规则匹配、BLEU 与 GPT 评分评价问题生成；工具使用以格式、API 匹配、正误率和最终任务结果评价信息收集是否有效；最终规划质量则评估是否完成用户目标。这说明澄清并不是独立步骤，而是支持执行策略的前置条件。

在评价层面，给定材料呈现出不同的评价单位与训练信号，不能简单视为一条从静态到过程性的单线演进。Qulac 一线 [R21] 与 MIMICS 数据集 [R23] 以及面向搜索的多轮澄清设定，更关注“何时提问”和“问什么”；而 ClarifyGPT [R34] 和 Ask-before-Plan [R37] 则更关注“澄清是否帮助下游任务完成”。对 Personal Agent 而言，真正重要的是澄清是否改变了用户状态、是否减小了方案不确定性，并是否带来了更好的后续行为。

交互澄清方式的适用条件与代价同样需要正面讨论。首先是“是否问”的判断成本：不是所有含糊请求都值得打断用户，Horvitz 的混合主动原则 [R33] 把主动程度视为代理估计收益、成本和用户偏好时的权衡问题。其次，是“问什么”的成本：如果澄清问题过于泛化，用户会感到打扰；如果问题过于细，可能使系统忽略更重要的需求层面。最后，澄清会影响用户信任与体验，因此需要明确何时停止澄清、什么样的确认才足够支持后续行动。

现有澄清研究已经覆盖搜索、问答、代码与工具支撑的规划，比较重点应从是否存在闭环转向闭环中哪些能力得到验证。[R21][R22][R34][R37] 以及后续的 RegretBench [R40] 为 Personal Agent 提供了更具体的比较工具：它们不再只评价“会不会问”，而是评价“是否问在正确时机、问得是否有价值，并帮助形成更好的回应”。

### 本节比较与评价

需求不确定性的评价应区分理解、澄清策略与最终协助。DialogUSR 和 BlendX 分别提供复杂话语拆分与混合意图数据，用于检查显式请求成分的处理；澄清任务则更关注会话中是否识别到歧义、是否提问得当以及是否减少决策不确定性。RegretBench 进一步将澄清作为多轮策略评价：在隐藏意图与语义状态框架下，以终端意图匹配衡量成功，以轮次、成本和无效澄清等诊断解释交互代价。

这些评测为个人协助提供了更具体的比较工具，但模拟用户的成本不直接等于真实人的负担。对 Personal Agent，还应记录澄清后回应方向是否改变、用户是否接受澄清并继续交互、哪些澄清导致了更好的长期利用率等指标。这样才能把“发问能力”真正转化为“理解与支持能力”。
