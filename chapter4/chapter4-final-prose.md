# 第四章 个性化回应与持续更新

_Personal Agent 白皮书第四章正式工作稿 · 2026-10-03_

第三章讨论 Personal Agent 如何形成对具体用户的长期理解。本章进一步讨论这种理解如何进入当前回应：用户已经提出明确问题时，系统需要给出���确、可靠的回答；用户提出的是协助需求时，系统需要根据其个人背景与偏好调整回应；用户的需求不完整时，系统需要通过澄清与方案确认逐步逼近真实需求。

这三个层次对应不同的研究对象。回答可靠性需要处理问题与证据的关系，个性化协助需要处理用户差异与生成行为的关系，需求澄清需要处理系统对需求不确定性的管理与控制。它们共同构成 Personal Agent 在单轮回应里的核心能力边界。

本章范围限定为当前轮次及其必要的澄清、修改与方案确认。回应结果怎样进入长期用户状态、系统怎样在后续时机提供主动支持，由第五章展开。

本章采用任务层次与方法机制相结合的分类：二级标题区分回答、协助和需求澄清，4.2 的三级标题比较用户条件的接入方式，4.3 的三级标题比较利用已有信息与交互澄清的对照。

## 4.1 明确问题的客观回答

明确问题指用户已经提出相对清楚、可被回应的目标；其中仍可能存在需要局部确认的条件，其核心在于系统依据何种信息、以何种方式给出客观回答，并在必要时识别回答无法成立的边界。

从事实查询的机制看，参数化知识与外部检索的结合是代表性路线。RAG[R03]将预训练序列到序列模型作为参数化记忆，将Wikipedia的稠密向量索引作为非参数化知识来源；两者共同支持针对当前问题的直接回答。Self-RAG[R04]正是在这一点上与RAG形成互补：它批评无差别地检索固定数量段落、不区分检索是否必要或段落是否相关的做法，会削弱模型通用性或导致过度检索。

回答目标不同，评价维度也随之分化。ALCE[R02]针对LLM生成带引用文本的需求，构建了自动引用评价基准，沿流畅性、正确性和引用质量三个维度设计评价指标。

当回答依赖个人历史与长期记忆时，问题的性质发生变化，回答依据从公共语料转向私人对话历史。LongMemEval[R05]将长期记忆拆解为信息抽取、跨会话关联、时间推理和拒答等能力，并用真实或合成长对话评估模型在长期语境中的表现。

客观回答还必须包含拒答边界。LongMemEval[R05]明确将拒答列为五种长期记忆能力之一，即当所需信息不存在于记忆中时，系统应当承认不可知而非编造。

个性化条件下的客观回答引入新的张力。PERGData[R15]认为既有评价主要关注回应是否符合用户偏好，而事实性同样重要却常被忽视，并据此定义个性化回答中的事实正确性要求。

对Personal Agent而言，上述工作给出的启示是分层的：对“帮我安排学习计划”这类涉及个人背景的请求（此为本文的分析例子，不是论文案例），客观回答需要区分“用户事实能否支持当前判断”与“是否必须从个人历史中提取所需信息”。因此，系统需在回答阶段同时控制证据来源、证据可信度和信息超界。

## 4.2 用户特征驱动的个性化协助

本节按用户信息影响回应的主要机制比较方法。第一类把已选用户条件组织为显式画像和提示，第二类随当前任务从历史中检索相关材料，第三类将用户表示与底座模型的参数适配结合起来。三类方法都围绕同一核心问题展开：同一个请求在不同用户背景下应如何产生不同处理。

解释、建议和计划是各类路线共同面对的输出任务；候选比较与用户协商是各类方法都需要满足的交互要求。本文因此将它们纳入机制分析和统一评价框架。

### 4.2.1 基于用户画像与提示的个性化协助

上一节讨论明确问题条件下的客观回答机制，其共同假设是回应所需条件主要来自当前对话上下文与检索到的材料。然而在 Personal Agent 的使用场景中，很多协助需求依赖用户背景、偏好和使用习惯，而不是单纯的事实检索。

在表示环节，最有代表性的两条路线是 GPG 提出的引导式画像生成 [R07] 和 PQA 提出的动态画像生成与压缩 [R08]。二者的共同点在于都不直接把原始个人上下文塞进提示，而是先构造一个更适合生成的用户摘要。GPG 通过提示模型从用户历史中生成结构化的个人描述；PQA 则进一步强调画像的压缩与更新，允许根据当前任务抽取最相关的个人信息。

这两条路线的关键分歧点在于压缩方式与信息损失的取舍。GPG 将个人上下文压缩为“简洁、描述性句子”，保留自然语言的连续表述，优点是可读且方便进一步修订；PQA 更关注高相关字段和压缩后的表述，强调在高噪声历史中保留有用个人特征。两者都说明画像不是单纯记忆回放，而是有筛选和组织过程的用户状态表示。

在接入环节，两条路线都采取将画像文本置入提示以条件化生成的方式，但接入的组织粒度不同。GPG 将提炼后的画像句子整体用于生成 [R07]；PQA 则把用户画像拆成更细粒度的字段和状态条件，作为当前任务的辅助输入 [R08]。

在评价方面，可以区分两类证据。GPG 报告其在不同任务上提升了 LLM 的个性化能力，例如与直接喂入原始个人上下文相比，在预测个人偏好上提升 37% 左右；PQA 在长文本问答等任务中展示了更稳定的个性化生成效果。任务型协助场景的评价还需要专门的设置。PersonaLens 作为面向任务型 AI 助手的个性化评测基准，提供带丰富偏好和交互历史的多样化用户画像，并通过模拟任务对话评价输出是否符合用户特征。

就适用条件而言，画像—提示路线的约束可以从三方面归纳。第一，表示质量的上界由原始个人上下文决定：GPG 与 PQA 都假设存在可用的个人上下文，且需要能够提取较稳定的偏好或背景。第二，画像偏重“对当前任务可用”的信息，而非完整的个人全景，因此如何定义压缩保留边界非常重要。第三，过度压缩可能损失细节，导致本轮回答看似个性化，实则忽略了具体动机或上下文变化。

画像提示为个性化协助提供了可读的条件表示，GPG 和 PQA 分别说明引导提炼、领域组织与压缩可以改善个人信息的利用。[R07][R08] 后续评价已经覆盖偏好预测和长文本生成等任务，但在 Personal Agent 场景中还需要进一步判断其是否支持用户计划、解释和决策的具体协助。

### 4.2.2 基于用户历史检索的个性化协助

个���化协助的一个核心问题是：模型在回应“帮我安排学习计划”或“我该怎么回导师”这类请求时，应该引用哪段历史，以及这些历史应如何改变当前方案。

这一机制的代表性工作可以从 LaMP 说起。需要先区分两个层面：LaMP 本身是一个用于训练和评估个性化输出的 benchmark，包含七个个性化任务，覆盖三个层次：偏好、过去行为和人格相关表达；LaMP-QA 则将类似思路推进到长文本问答场景。该 benchmark 面向个性化长文本答案生成，覆盖艺术与娱乐、生活方式与个人发展、社会与文化三大类共 45 个以个人偏好为核心的问答样本。

从“如何选择历史”的角度看，上述两项工作分别提供了不同维度的约束。LaMP 的检索模型比较体现的是相关性维度：用词项匹配还是语义匹配去对齐目标与历史；LaMP-QA 更强调长文本背景如何用于生成个性化回答。二者共同提示，一段历史如果不与当前任务匹配，就不能作为个性化生成的有效前提。

然而，这些 benchmark 主要评测的是记忆或个性化能力，不能直接等同于协助效果的证明。LoCoMo 的数据可以说明长期历史本身的难度：其对话平均包含 600 多轮、跨多个月的上下文，长期记忆检索因此比短期对话更容易出现不一致、遗忘和误用。也就是说，历史检索不仅需要“找得到”，还需要“找得对”。

历史检索的协助效果应在任务层面检查。LaMP-QA 关注生成答案与人类偏好的一致性，PersonaLens 则通过模拟任务对话联合评价个性化、回应质量与任务结果。在更接近 Personal Agent 的动作与计划任务中，候选方案的个性化价值必须以最终产物为核心：例如网页协助中重点看函数参数是否被更准确地填充，学习计划中重点看建议是否与用户知识基础和时间约束相匹配。

历史检索的评价需要同时检查是否找对了用户材料，以及这些材料是否被忠实使用。用户偏好不应覆盖客观事实，检索得分与最终回应质量也不是同一个维度；系统可能找到相关历史，但仍可能把它用于错误的推断或过度泛化。PersonalWAB 与 Behavior2Trip 这类工作进一步提示，历史选择需要和下游行动相连：如果检索到的用户背景不影响工具选择、参数设置或计划制定，那么它就不能被视为真正有用的个性化依据。

综合来看，基于用户历史检索的个性化协助的适用条件可以概括为：任务确实依赖用户特有的背景（如个人日程、过往讨论、既有偏好）；历史中存在可识别的条件与证据；且当前协助要依赖这些条件来决定方案差异。对 Personal Agent，这意味着历史不是泛泛“记住用户”，而是“当前回应需要、且当前回应可被追溯的材料”。

### 4.2.3 基于用户表示与模型适配的个性化协助

在 4.1 所处理的明确问题直接回应之外，个性化协助的核心问题在于：相同的请求在不同用户背景下应有不同处理。以“帮我安排学习计划”这一分析例子为例，用户 A 是已有基础、希望高强度效率提升；用户 B 则更在意认知负担和可持续性。两者的最优协助并不相同，问题在于如何把用户表示转化为生成策略。

第一条路线以 PPlug [R09] 为代表。其摘要指出，为每个用户单独微调一个个性化 LLM 代价过高，难以普及；而检索式方法将用户历史中相关文本作为示例，放到提示中进行个性化生成。第二条路线则以 Chameleon（Fake it then Align it）[R10] 为代表。其摘要同样指出逐用户微调成本过高，并补充了检索式路线的另一约束：检索方法依赖大量额外历史和有效规则，而个性化模型需要在真实用户行为和期望行为之间做对齐。

PUMA 展示了历史检索与参数级对齐的组合：任务相关记忆先提供当前条件，监督微调与直接偏好优化再适配模型的动作生成。[R36] 它与 PPlug 的输入嵌入方式相比，更强调将用户历史转化为可供模型优化的训练信号，而不只是在推理阶段做提示增强。三者共同说明，个性化可以发生在输入层、表示层和参数层三种位置。

比较两条路线，可以提炼出若干适用条件。在用户数据需求方面，PPlug 需要对用户全部历史上下文建模，数据数量、连续性和噪声都会影响表示；Chameleon 则通过生成偏好数据降低逐用户采集代价，但仍要求存在可用的偏好建模目标。不同机制在“训练成本、数据要求和输出稳定性”上存在明显差异。

评价方面，PPlug 与 Chameleon 在 LaMP 上的任务指标支持其各自设定下的个性化收益，不能直接证明多轮协助的有效性。[R09][R10][R11] PersonaLens 的模拟任务评测提供了更接近真实协助场景的参考，但仍需结合实际用户反馈进行校正。表示接入与模型适配都需要检查事实性风险。PERG 将事实准确和偏好匹配作为联合要求，这为评价个性化收益提供了补充维度。[R15] 对学习计划等协助任务尤其重要，因为错误的历史利用可能让回答看似贴合用户，但在事实层面已偏离真实信息。

表示接入、表征编辑与参数训练提供了不同的个性化位置。PPlug 保持底座参数不变，以用户嵌入接入历史；Chameleon 使用自生成偏好数据与表示编辑；PUMA 进一步说明参数适配可以强化模型对用户偏好的长期稳定性。对 Personal Agent 而言，这些机制并非互斥，而是可以在不同责任边界中组合：例如先用记忆与画像提供“当前输入条件”，再用少量偏好数据修正输出策略。

## 4.3 不完整需求的澄清与回应组织

本节按回应所依赖的信息来源比较两种处理方式：一是利用已有话语、用户条件与当前情境理解需求，组织可纠正的条件化回应；二是通过提问、候选方案和交互确认，以更低成本收集缺失信息并逐步逼近真实需求。

### 4.3.1 基于已有信息的需求理解与回应

本节讨论的核心问题是：在可用的用户信息与当前情境证据之上，系统如何组织本轮回应。传统任务型对话系统倾向于把回应生成视为“意图到动作”的映射；但 Personal Agent 的问题通常更复杂，往往需要把需求拆解为事实需求、行动需求、情绪需求和约束条件，并据此组织一轮回复。

基于已有信息的处理方式的第一类基础工作关注复杂话语的结构化整理。DialogUSR [R27] 针对用户在单一话语中表达多个意图的现象，提出先将其拆分为多个子需求，再分别解析；BlendX [R28] 进一步扩展到更复杂的混合意图检测场景，这类能力对 Personal Agent 的多目标支持很关键。

第二类工作强调回应必须嵌入情境才有意义。Dey [R32] 对情境建模的经典论述指出，时间、地点、活动和社会情境可以改变当前信息的意义；这一原则在 Personal Agent 中尤其重要，因为“我今天不想继续”同样的表述，可能在工作日、休息日、健康状态差或人际关系紧张时具有不同的实际意义。

情境解释还需要判断哪些个人信息与当前需求有关。RPEval 将偏好使用区分为 Ignore、Support 和 Dominate：有的偏好应被忽略，有的作为辅助条件，有的决定最终动作，这说明系统不能简单把用户画像全部嵌入回应，而要判断“这条偏好现在是否适用”。

第三类工作处理的是表面任务之外的支持需要。ESConv [R29] 定义了情绪支持对话任务，其框架建立在帮助技能理论之上，数据集中对支持策略（如安慰、共情、重构认知等）做了区分。这类需求不是单纯命令式提问，而是在用户情绪与状态不足时提供缓冲和方向。

多类需要并存时的组合问题由相邻工作揭示。Blended Skill Talk [R31] 指出，吸引人、有知识、有共情等品质此前多被孤立训练，而良好的开放域对话应当同时兼顾信息质量、关系维持和行动支持。对 Personal Agent，这意味着一轮回应往往需要同时处理事实、偏好与情绪，不能被简化为单一任务的生成。

适用条件方面，基于已有信息的处理方式要求已有话语与情境信息足以形成一个有依据的假设。当用户表达明确且情境充分时，系统可给出条件化的、可纠正的回应；但如果需求仍未稳定，系统就需要进一步澄清。对 Personal Agent 而言，现有工作的价值在于提供了明确“什么是已知条件、何时可以组织回应”的边界，并说明回应中应如何保留修正空间。

### 4.3.2 基于交互澄清的需求细化与回应

在进入具体方法之前，需要先界定本节要处理的问题：当用户的请求本身不足以支持唯一的回应时，系统应当如何组织这一轮的回应。与 4.3.1 讨论的“在已有信息下组织回答”不同，本节关注的是“需求尚未稳定，需要与用户互动才能确定”。

从问题界定转向机制比较，最早形成体系的一类工作来自开放域信息寻求对话领域。Aliannejadi 等人在 SIGIR 2019 的工作 [R21] 研究了信息需求不完整时如何生成澄清问题；其后由 MIMICS [R23] 与 MIMICS-Duo [R24] 等工作扩展到更大规模的搜索澄清设置，说明澄清并不是简单“追问”，而是为了确定用户真实意图和候选项差异。

第二类机制差异体现在澄清问题的生成与排序如何借助外部内容支撑。Mass 等人的混合主动会话搜索工作 [R25] 明确将任务设定为：在给定对话上下文的基础上，决定何时提问、提什么问题，并在候选检索结果中选择证据以支持澄清。此类工作强调澄清必须有“信息增益”，不是仅仅为了显得主动。

模型对歧义的处理还可以通过训练改变。APA 利用模型自身对歧义的感知进行对齐，使其显式检测和管理歧义查询，同时保留明确问题上的作答能力 [R26]。这说明澄清不是外部规则的简单插入，而可以成为模型行为策略的一部分。

第四类差异来自领域特化的澄清框架。ClarifyGPT [R34] 面向代码生成：它先通过代码一致性检查判断给定需求是否含歧义，若有歧义则提示大模型生成有针对性的澄清问题，以便收敛到可执行的任务定义。Ask-before-Plan [R37] 则把澄清扩展到真实世界规划：系统在做计划前检测是否需要先收集额外信息，再基于可用工具和环境状态推进行动。

澄清与下游协助的关系还可以在计划任务中检验。Ask-before-Plan 的指标对应三个子任务：Clarification Accuracy 检查澄清需要预测，规则匹配、BLEU 与 GPT 评分评价问题生成；工具使用以格式、API 匹配、正误率和最终任务结果评价信息收集是否有效；最终规划质量则评估是否完成用户目标。这说明澄清并不是独立步骤，而是支持执行策略的前置条件。

在评价层面，给定材料呈现出不同的评价单位与训练信号，不能简单视为一条从静态到过程性的单线演进。Qulac 一线 [R21] 与 MIMICS 数据集 [R23] 以及面向搜索的多轮澄清设定，更关注“何时提问”和“问什么”；而 ClarifyGPT [R34] 和 Ask-before-Plan [R37] 则更关注“澄清是否帮助下游任务完成”。对 Personal Agent 而言，真正重要的是澄清是否改变了用户状态、是否减小了方案不确定性，并是否带来了更好的后续行为。

交互澄清方式的适用条件与代价同样需要正面讨论。首先是“是否问”的判断成本：不是所有含糊请求都值得打断用户，Horvitz 的混合主动原则 [R33] 把主动程度视为代理估计收益、成本和用户偏好时的权衡问题。其次，是“问什么”的成本：如果澄清问题过于泛化，用户会感到打扰；如果问题过于细，可能使系统忽略更重要的需求层面。最后，澄清会影响用户信任与体验，因此需要明确何时停止澄清、什么样的确认才足够支持后续行动。

现有澄清研究已经覆盖搜索、问答、代码与工具支撑的规划，比较重点应从是否存在闭环转向闭环中哪些能力得到验证。[R21][R22][R34][R37] 以及后续的 RegretBench [R40] 为 Personal Agent 提供了更具体的比较工具：它们不再只评价“会不会问”，而是评价“是否问在正确时机、问得是否有价值，并帮助形成更好的回应”。

### 本节比较与评价

需求不确定性的评价应区分理解、澄清策略与最终协助。DialogUSR 和 BlendX 分别提供复杂话语拆分与混合意图数据，用于检查显式请求成分的处理；澄清任务则更关注会话中是否识别到歧义、是否提问得当以及是否减少决策不确定性。RegretBench 进一步将澄清作为多轮策略评价：在隐藏意图与语义状态框架下，以终端意图匹配衡量成功，以轮次、成本和无效澄清等诊断解释交互代价。

这些评测为个人协助提供了更具体的比较工具，但模拟用户的成本不直接等于真实人的负担。对 Personal Agent，还应记录澄清后回应方向是否改变、用户是否接受澄清并继续交互、哪些澄清导致了更好的长期利用率等指标。这样才能把“发问能力”真正转化为“理解与支持能力”。
